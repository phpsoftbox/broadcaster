# Server

`PushrServer` запускает WebSocket сервер и принимает подключения.

```php
$server = new PushrServer(
    apps: new PushrAppRegistry(['app-1' => 'secret-1']),
    host: '0.0.0.0',
    port: 8080,
    maxSkew: 300,
    pingInterval: 25,          // ping простаивающим соединениям, 0 — выключить
    idleTimeout: 60,           // закрытие молчащих соединений, 0 — не закрывать
    maxOutgoingBytes: 4194304, // лимит очереди исходящих байт одного соединения
    clock: null,               // Psr\Clock\ClockInterface, по умолчанию системное время
);

$server->run();
```

Сервер однопоточный (цикл `stream_select`), поэтому защищён от медленных клиентов: HTTP-handshake дочитывается
неблокирующе, соединение без завершённого handshake закрывается через 5 секунд, заголовки больше 16 КиБ отклоняются.
Кадр с payload больше 1 МиБ или некорректной длиной закрывает соединение.

## Исходящие данные

Отправка не блокирует цикл: кадры ставятся в очередь соединения и пишутся сразу, сколько примет сокет; остаток
дописывается, когда `stream_select` отмечает сокет готовым к записи. Поэтому большой кадр не обрезается и поток
кадров не ломается. Ошибка записи закрывает соединение (с освобождением каналов). Если очередь превысила
`maxOutgoingBytes` (по умолчанию 4 МиБ) — клиент не читает данные, соединение закрывается.

## Keepalive

Сервер следит, что соединения живы, по времени последнего входящего кадра любого типа (текст, ping, pong, close);
отсчёт начинается с завершения handshake. Проверка идёт в цикле `run()` (select просыпается раз в секунду):

- соединению, от которого ничего не приходило `pingInterval` секунд (по умолчанию 25), отправляется ping
  (opcode 9), не чаще одного за интервал;
- соединение без входящих кадров `idleTimeout` секунд (по умолчанию 60) закрывается: close-кадр с кодом 1001
  (going away), каналы освобождаются. Так удаляются полуоткрытые соединения, которые NAT или прокси закрыли без FIN.

`idleTimeout` должен быть больше `pingInterval`, иначе `InvalidArgumentException`; `0` отключает соответствующую
проверку. `idleTimeout: 0` возвращает поведение до keepalive: молчащие соединения не закрываются.

Браузеры и стандартные WebSocket-библиотеки отвечают на ping сервера автоматически. Собственный клиент должен
отвечать на ping (opcode 9) pong'ом (opcode 10) или периодически слать прикладной ping — иначе сервер отключает его
каждые `idleTimeout` секунд. `PushrClient` отвечает на ping сам при вызове `receive()`.

Сервер отвечает по RFC 6455: на ping — pong с тем же payload (не длиннее 125 байт), pong принимается молча,
на close — ответный close с кодом клиента, после чего соединение закрывается.

Если прокси перед сервером закрывает простой короче 60 секунд, уменьшите `pingInterval` (и при необходимости
`idleTimeout`). CLI-опции: `--ping-interval`, `--idle-timeout` (см. [CLI](06-cli.md)).

### Прикладной ping

Браузерный JS не видит control-кадры, поэтому для проверки соединения со стороны клиента есть текстовое сообщение:

```json
{"type": "ping"}
```

Ответ:

```json
{"type": "pong"}
```

Прикладной ping, как и любой входящий кадр, сбрасывает таймер простоя.

Поддерживаемые сообщения от клиента:
- `ping` — прикладной ping, ответ `{"type":"pong"}` (см. [Keepalive](#keepalive))
- `subscribe` — подписка на канал (для приватных каналов нужен `auth`)
- `unsubscribe` — отписка
- `publish` — публикация события; только для соединений публикатора (`role=publisher`, см.
  [Авторизация](03-auth.md#публикация)), остальным — ошибка `Publish is not allowed for this connection`

Формат:

```json
{
  "type": "publish",
  "channel": "news",
  "event": "message",
  "data": {"text": "hello"}
}
```

## Подписка на приватный канал

```json
{
  "type": "subscribe",
  "channel": "private.user.10",
  "auth": "app-1:signature"
}
```

Для presence-каналов можно передать `channel_data`:

```json
{
  "type": "subscribe",
  "channel": "presence.chat",
  "auth": "app-1:signature",
  "channel_data": {"user_id": 1, "name": "Name"}
}
```
